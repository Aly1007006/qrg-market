# PHASE 5 — CustomerRequest / Lead

## Границы

Заявка — обращение к продавцу, не платёжный заказ. QRG не принимает деньги
покупателя, не проверяет оплату и не резервирует остаток. CONFIRMED означает
«Обращение подтверждено». Статусы NEW, VIEWED, CONTACTED, CONFIRMED, CLOSED,
REJECTED относятся только к общению. PHASE 6 не запускалась.

Существующие Next.js → NestJS → PostgreSQL, S3 и session authorization сохранены.
Новых dependencies/packages нет. Один товар на заявку: отдельная request_items
пока не нужна. Variant можно не выбирать; quantity 1–99 — пожелание покупателя,
не гарантия наличия.

## Database

Миграция `0004_grey_sue_storm.sql` добавляет enum и customer_requests.
В строке хранятся имя, нормализованный телефон, товар/вариант, количество,
предпочтение получения, комментарий, статус, timestamps и снимки названия
товара/варианта. Изменение товара не переписывает содержание старого обращения.

Согласие фиксируется типом PRIVACY, server-controlled версией request-privacy-v1,
временем БД и ID самой заявки. Строка создаётся только при `privacyConsent=true`;
маркетинговое согласие не запрашивается и не подразумевается.

FK `(product_id, shop_id)` и `(variant_id, product_id, shop_id)` исключают смешение
магазинов. Новый unique index варианта обеспечивает цель второго FK. Удаление
связанного магазина/товара/варианта ограничено RESTRICT; архивирование допустимо.
Удаление пользователя, последним изменившего статус, оставляет заявку и обнуляет
status_changed_by. Нет cascade-удаления обращений. CHECK ограничивают телефон,
количество, строки, pickup, тип согласия и формат HMAC-хэшей.

Индексы: shop/created/id, shop/status/created, product, variant, status actor,
dedup/created и unique submission hash. Trigger поддерживает updated_at даже
при SQL update вне ORM. Все даты хранятся как timestamptz.

## API

Все пути ниже относительно `/api/v1`:

| Метод / путь                                | Доступ / назначение                                                 |
| ------------------------------------------- | ------------------------------------------------------------------- |
| GET `/public/requests/challenge/:productId` | Гостевой challenge только для PUBLISHED товара ACTIVE магазина      |
| POST `/public/requests`                     | Без аккаунта, 202 `{accepted:true}`, без cookies и PII в ответе     |
| GET `/shops/:shopId/requests`               | requests.read, page/limit/status, телефон и комментарий не включены |
| GET `/shops/:shopId/requests/:requestId`    | requests.read, защищённая карточка                                  |
| PATCH `/shops/:shopId/requests/:requestId`  | requests.write, только status и expectedStatus                      |

Owner/manager/employee имеют requests.read/write только через актуальную membership.
Подмена shopId/requestId не даёт доступа; чужой ресурс возвращает 404.
Поля shop_id, owner_id, role, permissions, status в гостевом DTO не принимаются.
Магазин вычисляется из товара в транзакции. Seller mutation требует сессию и CSRF.
Не существует публичного списка/карточки заявок.

При смене статуса expectedStatus предотвращает перезапись параллельного изменения
(409). Возврат обработанного обращения в NEW запрещён. Остальные статусы можно
изменять вручную; чтение само по себе не переводит в VIEWED.

## Input / anti-spam

- JSON-only, Origin и x-qrg-client проверяются в Next BFF и Nest. Cross-site запросы
  запрещены; гостевой BFF не пересылает cookie или authorization.
- Лимит гостевого JSON 8 KiB и в BFF, и в Nest; BFF считает байты потока даже без
  Content-Length. Сжатые payload не принимаются. Общий API лимит 32 KiB сохранён.
- DTO reject unknown fields. NFC + trim для текстов, ограничения длины,
  отклонение HTML/опасных управляющих символов. Только plain text, React escaping.
- Телефон нормализуется существующим валидатором в международный E.164.
- Honeypot, подписанный HMAC challenge с привязкой к товару и случайным nonce:
  не ранее 2 секунд и не позднее 30 минут. Это препятствия для спама, не CAPTCHA.
- На 15 минут: GET challenge 120, POST 30 на реальный socket IP; 5 прошедших
  начальную валидацию попыток на нормализованный телефон. Ошибка 429 + Retry-After.
  Ключи rate limit — HMAC; raw IP не хранится и X-Forwarded-For не считается доверенным.
- CaptchaVerifier — заменяемый adapter. При REQUEST_CAPTCHA_REQUIRED=true без
  настоящего провайдера возвращается 503, а не имитация успешной проверки.
- Submission token хранится только в виде HMAC. Повтор того же token/payload
  идемпотентен; изменённый payload с тем же token получает 409. Одинаковые данные
  с новым token в течение 15 минут не создают дубль. Транзакционные advisory locks
  и UNIQUE защищают одновременные отправки. После истечения challenge нужна новая форма.

Ограничение, перенесённое из foundation: за Next BFF пользователи делят upstream
IP quota (30 POST / 15 минут). Перед публичным запуском нужен доверенный proxy
boundary для отдельного client IP, без принятия произвольных forwarded headers.
Телефон не подтверждается OTP: это контакт для ответа, не verified identity.

## UI и WhatsApp

Product Page сохраняет точный текст: «Оплата производится напрямую продавцу.
QRG MARKET не принимает оплату за данный товар.» Форма не требует регистрации;
checkbox согласия не включён заранее. Успешный ответ не означает резерв/оплату.
Список и карточка заявки находятся в существующем seller dashboard, с фильтром
статуса и пагинацией. Контакты видны только в авторизованной карточке, не в списке.

Номер WhatsApp задаётся владельцем через уже существующий Contacts API,
нормализуется backend и дополнительно проверяется frontend-контрактом.
Отсутствующий/невалидный номер не превращается в активную ссылку.
`https://wa.me/<digits>?text=...` строится через URLSearchParams; имя и телефон
покупателя в URL не попадают. Текст включает товар и выбранный вариант.
Ссылка открывает draft; отправку подтверждает сам пользователь.
Формат соответствует [официальной документации WhatsApp](https://faq.whatsapp.com/5913398998672934).

## Privacy и запуск

`CUSTOMER_REQUESTS_ENABLED`: development/test по умолчанию true, production false.
Недопустимое значение останавливает запуск. Отключение блокирует guest challenge
и создание, но не чтение продавцом уже существующих заявок.

`/privacy/requests` описывает фактические поля, цель, передачу выбранному магазину
и исключение маркетинга. Это подготовленный текст, не заявление о завершённой
юридической проверке. До production необходимо утвердить и опубликовать:

- реквизиты оператора QRG и privacy-контакт;
- сроки хранения и процесс исправления/удаления/отзыва согласия;
- инфраструктуру основной БД, encrypted backup и логов с персональными данными
  в Казахстане, права runtime DB user и проверенное восстановление.

После изменения текста условий нужно синхронно повысить policy version API/UI.
Автоматическое удаление заявок не введено без согласованного срока хранения;
это незавершённая эксплуатационная задача до production, а не бессрочная политика.
Нет публичного удаления по телефону: без проверки личности это могло бы удалить
чужие обращения. Requests не добавляются в body logs/analytics.

## Проверки и обслуживание

`pnpm test:requests` компилирует и запускает 10 PostgreSQL/HTTP проверок на `_test`
БД. После него и `pnpm build` команда `pnpm test:requests:smoke` повторяет их и
добавляет built Next → Nest → PostgreSQL guest/seller flow (порт 43186).
Тестовые заявки очищаются адресно до удаления fixture-магазинов.
`pnpm db:cleanup` продолжает очищать истёкшие HMAC rate-limit записи.
Новые suites добавлены в CI; deploy не добавлен.
