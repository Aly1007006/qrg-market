# Запуск QRG Market на Hoster VPS

Этот план предназначен для первого контролируемого запуска на Hoster VPS.
Он не заменяет production-архитектуру Yandex Cloud из `production-architecture.md`:
один VPS не обеспечивает независимую отказоустойчивость. До покупки отдельной
управляемой базы он подходит только для ограниченной beta-эксплуатации.

## Рекомендуемый сервер

- Hoster Cloud 4-8-200: 4 vCPU, 8 GiB RAM, 200 GiB NVMe, один IPv4;
- Ubuntu 24.04 LTS;
- отдельный домен для публичного сайта;
- отдельное зашифрованное хранилище резервных копий в Казахстане.

Не устанавливать Plesk или ISPmanager: приложение разворачивается контейнерами,
а не как PHP-сайт.

## Что размещается на сервере

| Компонент                 | Доступ из интернета              |
| ------------------------- | -------------------------------- |
| HTTPS reverse proxy и web | только 80/443                    |
| API                       | только из web/reverse-proxy сети |
| PostgreSQL + PostGIS      | только приватная Docker-сеть     |
| хранилище медиа           | только приватная Docker-сеть     |
| SSH                       | только с адресов администраторов |

Порты API, PostgreSQL, storage, Docker daemon и панели управления не публикуются.
Для SSH использовать ключи, отключить вход по паролю и запретить root-вход.

## До первого публичного клиента

1. Купить VPS и домен, но не направлять DNS на сайт.
2. Создать отдельного системного пользователя для deploy, настроить обновления
   безопасности, firewall и вход по SSH-ключу.
3. Создать production secrets вне Git: пароли базы, `AUTH_RATE_LIMIT_SECRET`,
   `INTERNAL_PROXY_SECRET`, ключ MFA администратора и ключи хранилища медиа.
4. Развернуть закрытый staging на временном поддомене и выполнить миграцию
   отдельной migration-ролью. Runtime API не должен получать DDL-права.
5. Настроить HTTPS, health-checks, перезапуск контейнеров и уведомления о
   недоступности, высокой нагрузке, заполнении диска и неуспешном backup.
6. Настроить ежедневный зашифрованный backup PostgreSQL и медиа во второе
   независимое KZ-хранилище.
7. Выполнить restore drill в отдельное окружение: проверить восстановление БД,
   медиа, вход администратора и публичный каталог.
8. Создать первого SUPER_ADMIN и завершить TOTP MFA + проверку recovery-кодов.
9. Открыть ограниченную beta для 5–10 бутиков. До завершения payment acceptance
   подписки не списываются автоматически.

## Отдельно до монетизации

Автоматические платные подписки остаются выключенными, пока не завершены:

- Halyk merchant onboarding и официальный контракт callback-подписи;
- тест успешной, неуспешной и повторной оплаты;
- серверная проверка статуса платежа и сверка ledger;
- реальная доставка писем восстановления пароля;
- утверждённые правила обработки и хранения клиентских обращений.

Платная кнопка или redirect после банка не являются доказательством оплаты.
Сначала допускается beta с ручным сопровождением подписок и прозрачными условиями.

## Что понадобится от владельца

- доступ к аккаунту Hoster после покупки VPS;
- выбранный домен;
- email/телефон для уведомлений о сбоях;
- решение о сроке хранения клиентских заявок;
- данные Halyk только после оформления merchant account.

Никогда не отправлять секреты, root-пароли, SSH private keys или банковские
данные в GitHub, чат или `.env` из репозитория.
