# Правила внесения изменений в проект (CONTRIBUTING.md)

Документ определяет стандарты разработки, ветвления, проверки качества и информационной безопасности для всех участников проекта **QRG MARKET**.

---

## 1. Требования к окружению

- **Node.js**: `24.20.0` (строго зафиксирован в `.node-version` и `package.json`).
- **pnpm**: `11.26.0` (строго зафиксирован в `packageManager`).
- **Окончания строк**: строго **LF (`\n`)** для всех файлов исходного кода (`.js`, `.mjs`, `.ts`, `.tsx`, `.css`). Символы CRLF (`\r\n`) и UTF-8 BOM запрещены и блокируются скриптом `pnpm source:check`.

---

## 2. Правила работы с ветками и коммитами

1. **Основная ветка (`main`)**:
   - Ветка `main` всегда должна находиться в рабочем состоянии и проходить все проверки CI.
   - Для крупных задач, изменений схемы БД или правок безопасности создавайте отдельную ветку:
     - `feat/<краткое-описание>` — новая функциональность (например, `feat/seller-quick-add`).
     - `fix/<краткое-описание>` — исправление ошибки (например, `fix/catalog-filter-reset`).
     - `docs/<краткое-описание>` — обновление документации.
     - `refactor/<краткое-описание>` — рефакторинг без изменения внешнего поведения.

2. **Рекомендуемый настрой Branch Protection в GitHub**:
   В настройках репозитория (`Settings → Branches → Add branch ruleset / branch protection rule` для `main`) рекомендуется включить:
   - **Require a pull request before merging** (если хотите обязательно проверять изменения друг друга перед слиянием) или оставить прямой пуш для двух администраторов, но обязательно включить **Require status checks to pass before merging** (`Quality` и `Docker Build`).
   - **Block force pushes** (запрет `git push --force` в `main`, чтобы никто случайно не перезаписал историю коммитов).

## 3. Обязательные проверки перед отправкой изменений

Перед каждым коммитом или открытием Pull Request выполните в корне проекта:

```powershell
# 1. Автоформатирование кода через Prettier
pnpm format

# 2. Проверка отсутствия CRLF и UTF-8 BOM
pnpm source:check

# 3. Строгая проверка типов TypeScript
pnpm typecheck

# 4. Проверка линтером ESLint
pnpm lint

# 5. Запуск unit-тестов API и Web
pnpm test

# 6. Проверка сборки обоих приложений
pnpm build
```

Если вы изменяли схему базы данных (`apps/api/src/db/schema.ts`), миграции (`apps/api/drizzle/`) или логику API, дополнительно запустите интеграционные тесты БД:

```powershell
pnpm test:db
pnpm test:smoke
```

## 4. Правила информационной безопасности (Обязательно к соблюдению)

1. **Никаких секретов в Git**:
   - Запрещено добавлять в коммиты реальные файлы `.env`, `.env.local`, `.env.test`, пароли от БД, токены API, приватные ключи (`*.pem`, `*.key`) и файлы состояния Terraform (`*.tfstate`).
   - Если появилась новая переменная окружения, добавьте её описание и безопасный шаблон в `.env.example`, `apps/api/.env.example` или `apps/web/.env.example`.
2. **Сохранение границ безопасности между Web и API**:
   - Клиентский браузер никогда не обращается к PostgreSQL напрямую.
   - Запросы из кабинета продавца (`/api/seller/...`) и админ-панели (`/api/admin/...`) проксируются через Next.js Route Handlers со строгой проверкой заголовка `Origin === QRG_APP_ORIGIN` и серверного секрета `QRG_INTERNAL_PROXY_SECRET`. Не ослабляйте эту проверку и не доверяйте заголовку `X-Forwarded-Host` от клиента.
3. **Защита от инъекций и невалидных данных**:
   - Все новые endpoints в NestJS должны использовать DTO с декораторами `class-validator`.
   - Запросы к БД выполняются только через параметризованные запросы Drizzle ORM.
4. **Безопасность загрузки файлов**:
   - Любые загружаемые изображения проходят валидацию магических байтов и перекодирование через `sharp` в `apps/api/src/media/`. Не разрешайте прямую загрузку SVG или необработанных файлов от пользователей.
5. **Безопасные миграции БД**:
   - Не изменяйте уже применённые файлы миграций `0000..0009` задним числом — создавайте новую миграцию через `pnpm db:generate`.
   - Не используйте `DROP TABLE` или `TRUNCATE` на рабочих данных.
